## 1. 背景：何が起きたか（D1 煙テスト）

論文ベンチの D1 煙テストでは、次の順に動きます。

```text
rbh（BLAST で相互最良ヒット）
  → orthopair（ゲノムペアごとのオーソログ表）
  → reorgOrthopairs（全ペアを1つのグラフにまとめ、多種のオーソグループ表を作る）
```

`rbh` と `orthopair` は正常に終わり、ペアごとの TSV も書けていました。  
問題は **`reorgOrthopairs()` の後半**です。

ログ上はだいたい次のメッセージまで出て、それ以降の進捗がありませんでした。

```text
[reorg] graph_qc=prune_weak: removing ... edges ...
[reorg] bridge inference: added ... edges ...
```

そのあとディスク上では次が書かれていました。

| 成果物 | 意味 |
|--------|------|
| `orthopair.graphml` | 全種をつないだオーソロジーグラフ |
| `bridge_inferred_edges.tsv` など | 橋渡し（bridge）で推論した辺 |
| `orthopair_list.tsv`（一部） | 小さい成分からのオーソグループ行 |
| `graph2df_tmp/g2df_0002` … `g2df_2572` | 並列に処理した「小さな／中くらいの成分」の途中結果 |

**欠けていたのは `g2df_0001` だけ**です。  
つまり「2571 個の成分は終わったが、**最初のジョブ（巨大成分）だけが終わらない**」状態でした。

観測としては次のように見えます。

- CPU がほぼ 100%（計算は続いている）  
- RSS（メモリ常駐量）が何時間もほぼ同じ（新しい大きな配列を増やしていない）  
- 出力ファイルが増えない（列挙が全部終わるまで結果を書かない）

→ **ハング（無限待ち）ではなく、終わらないほど重い計算**です。コンテナや BLAST の失敗ではありません。

## 2. reorg がやりたいこと（全体像）

OrthoPaiR のペア処理（`orthopair`）は、**2 ゲノムだけ**を見ます。  
`reorg` は、それらを全部まとめて「多種で一貫したオーソログの並び」を作ります。

イメージ:

```text
  イネ — オオムギ
  イネ — シロイヌナズナ
  イネ — ゼニゴケ
  オオムギ — シロイヌナズナ
  …（全ペアの辺）

        ↓ reorg が1つのグラフにする

  遺伝子を頂点、オーソログ候補を辺にした無向グラフ
        ↓
  連結成分ごとに「種ごとに高々1遺伝子」のまとまりを探す
        ↓
  orthopair_list.tsv（オーソグループ表）と pairwise 再出力
```

ここで出てくる重要概念を順に説明します。

### 2.1 グラフ・頂点・辺

| 用語 | OrthoPaiR での意味 |
|------|-------------------|
| **頂点（vertex）** | あるゲノムの1遺伝子（ID 付き） |
| **辺（edge）** | 「この2遺伝子はオーソログ候補」という関係。スコアは主に `mutual_ci` |
| **グラフ** | 頂点と辺の集まり（`igraph`） |

D1（4種）の例では、だいたい **約 8.4 万頂点・約 12 万辺**のグラフになっていました。

### 2.2 連結成分（connected component）

辺だけを伝ってたどり着ける頂点同士を、ひとまとまりにしたものが **連結成分**です。

- 小さな成分: 例）イネ遺伝子 A と オオムギ遺伝子 B だけがつながっている（2頂点）  
- 巨大成分: 弱い辺が次々に伸び、**数万の遺伝子が1つの巨大な塊**になっている

D1 の GraphML では、最大の連結成分が **約 4.3 万頂点**（全体の半分以上）でした。  
次に大きい成分は 100 頂点台で、**1000 頂点超は実質この1個だけ**です。

### 2.3 colorful subgraph（色付き部分グラフ）とは

OrthoPaiR では「1種から複数の遺伝子を同じオーソグループに入れない」制約を置きます。  
種を **色**、遺伝子を **色付き頂点**と考えると:

> **同じ色の頂点は高々1つ**だけ含む連結な集合を探す

これが **colorful**（種ごとに高々1遺伝子）という条件です。  
4種なら、1グループに入る遺伝子は最大4個です。

実装では、連結成分の中で **極大な colorful なクリーク（互いに辺で結ばれた集合）**を列挙し、それを `orthopair_list.tsv` の行にします。  
C++ 側の関数名は `cpp_em_max_cc_subg`（Bron–Kerbosch 系の列挙）です。

### 2.4 なぜ巨大成分だと終わらないのか

列挙アルゴリズムは、成分が少し大きくなると候補の組み合わせが爆発します。

- 4種なので「答えのサイズ」は最大4でも、  
- **探索の途中で見る頂点集合**は成分全体（4.3万）に依存する

さらに、実装上:

- 列挙が終わるまで **結果ファイルを書かない**  
- 作業用メモリは隣接リスト程度で足りるので **RSS は増えない**  
- CPU だけが回り続ける  

→ 「止まっている」ように見える、というのが D1 で起きたことです。

`max_components` という引数で「頂点数がこれより大きい成分は列挙をスキップ」できますが、煙テストではデフォルトの `Inf`（制限なし）のままだったため、巨大成分も列挙対象になっていました。

## 3. 「壊す」とはどういう意味か

ここで言う **壊す** は、生物学的に「オーソログ関係を捨てる」ことでは必ずしもありません。

正確には:

> **列挙（Bron–Kerbosch）に渡すグラフの連結性を、弱い糊でつながった巨大塊にしない**

つまり:

1. **強い辺（backbone）だけ**で連結成分を切り直す  
2. その小さい成分だけを colorful 列挙する  
3. 弱い辺・many-to-many・bridge は、**別の段階（augment）**で必要なら回収する  

「巨大成分を列挙する」のをやめて、「小さい成分を列挙し、弱い証拠は選択的に足す」に切り替える、という意味です。

これは reorg 改訂の北極星とも一致します。

- **やってよい:** bridge・スコア付きの選択的回収・colorful のルール改善  
- **やってはいけない:** 連結成分内の全クロスゲノムペアをオーソログにする（link_all）。ペア数が数百万〜になり、precision が崩れる

## 4. いまの処理順と、なぜ巨大成分が残るか

`reorgOrthopairs()` の中身を、初心者向けに簡略化すると次の順です。

```text
1. 各ペアの TSV を読む
2. 1つの igraph を作る（createGraph）
3. graph_qc = prune_weak（成分ごとに弱い辺を少し落とす）
4. bridge 推論（遠いゲノム間の欠けた辺を、中間ゲノム経由で足す）
5. GraphML を書く
6. graph2df: 連結成分ごとに colorful 列挙 → orthopair_list.tsv
7. 各種 augment（bridge や colourful の第2パスなど）
```

### 4.1 `prune_weak` がしていること

各連結成分の中で、`mutual_ci`（辺の強さ）の **下位 q%（既定 5%）** の辺を消します。  
Proteinortho 系の「flooding」の **とても簡略化した1回版**です。

D1 では約 1.1 万辺 / 12 万辺を消しましたが、**巨大成分は割れませんでした**。

理由のイメージ:

```text
とても弱い辺を5%落としても、
残った「まだ弱い many-to-many 辺」が全体をつなぎ続ける
```

実際のデータでは、巨大成分内の辺の大半が `MtoM` / `Mto1` で、`1to1` は少数でした。  
`mutual_ci` の中央値も低く、下位5%を一度切るだけでは「糊」が残ります。

### 4.2 bridge が巨大成分をさらに大きくしうる

bridge 推論は、例えば:

```text
イネ —（辺）— シロイヌナズナ —（辺）— ゼニゴケ
```

があるとき、イネ—ゼニゴケの辺が無い場合に、条件を満たせば **推論辺を足す**処理です。  
recall（取りこぼしを減らす）には有用ですが、グラフの連結性は増えます。

D1 では:

- bridge を除いても最大成分はまだ **約 6000 頂点**（列挙には大きすぎる）  
- bridge を入れると **約 4.3 万頂点**まで膨らむ  

つまり「prune_weak のあと bridge を足し、その全辺で成分を切って列挙する」現状だと、巨大成分に入りやすいです。

### 4.3 決定的な観察：どの辺を残すと成分が分かれるか

D1 の巨大成分（約 4.3 万頂点）に対し、「この種類の辺だけ残したら最大成分はいくつになるか」を測ると:

| 残す辺 | 最大成分の頂点数（目安） | 意味 |
|--------|--------------------------|------|
| 全部 | 約 43204 | 列挙不能 |
| direct のみ（bridge 除外） | 約 6053 | まだ列挙不能 |
| `class == "1to1"` のみ | **約 8** | 列挙可能 |
| `mutual_ci >= 0.5` | 約 66 | 列挙可能寄り |
| `mutual_ci >= 0.7` | 約 14 | 列挙可能 |

ここから分かることは単純です。

> **巨大成分をつないでいる糊は、主に弱い many-to-many と bridge である。**  
> **強い 1対1（backbone）だけにすれば、成分は自然に小さくなる。**

## 5. 「列挙前に壊す」具体的なやり方

方針は3層です。最初の1つが本命で、残りは保険です。

### 5.1 本命: 列挙用の backbone グラフを別に切る

**アイデア:**  
GraphML には弱い辺も残してよい。ただし **colorful 列挙に渡す辺は、強い辺だけにする**。

候補ルール（最初の実装として分かりやすいもの）:

1. **`class == "1to1"` の直接辺だけ**を列挙に使う（必要なら `strict` / `broad` に限定）  
2. または **`mutual_ci` が高い直接辺だけ**（閾値はデータで決める。D1 なら 0.5〜0.7 付近で十分小さい）

手順:

```text
A. 全辺グラフ G（いまどおり）を作る・QC・bridge を足す
B. 列挙用の辺集合 E_backbone を作る（例: 1to1 direct）
C. E_backbone だけで連結成分を計算し直す
D. 各小さい成分に対してだけ cpp_em_max_cc_subg を回す
E. 弱い辺・bridge・MtoM は、既存の augment で必要なら回収
```

ポイント:

- **成分の切り方を「全辺」から「backbone 辺」に変える**のが本質  
- いまの `.graph2df()` は、だいたい全辺（弱い bridge 含む）で成分を切っているので、頂点集合が 4.3 万のまま BK に入る  

D1 なら、1to1 backbone だけで最大成分が約 8 頂点まで落ちるので、列挙は普通に終わります。

### 5.2 保険: サイズ目標付きの反復 flooding

Proteinortho6 の flooding に近い形です。

```text
最大成分の頂点数 > T（例: 200）であるあいだ繰り返す:
  その成分の「いちばん弱い辺」を落とす
  （優先: 低 mutual_ci、非 1to1）
  成分を再計算する
```

いまの `prune_weak` との違い:

| | いまの `prune_weak` | 反復 flooding |
|--|---------------------|---------------|
| 回数 | 各成分で **1回** | **小さくなるまで**繰り返す |
| 目標 | 下位 q% を消す | 最大成分 ≤ T にする |
| 効果 | 巨大成分が残ることがある | サイズを直接制御できる |

backbone（§5.1）だけでは割れない成分が出たときに足す、という位置づけがよいです。

### 5.3 例外処理: それでも大きい成分への安全弁

backbone / flooding のあとも `|V| > T` なら:

- その成分だけ列挙をスキップする（既存の `max_components`）  
- または Fiedler ベクトルなどで二分割する（密行列は使わず、疎な固有ベクトル計算）

これは **例外処理**です。主戦場は §5.1 です。

注意: `max_components` で巨大成分を丸ごとスキップすると、その中の本物の 1to1 も colourful 列挙から落ちます。  
「飛ばす」は安全弁であって、「壊してから列挙する」の代替にはなりません。

### 5.4 落とした辺は捨てない

弱い `MtoM` や bridge を列挙から外しても、次には残します。

- GraphML（可視化・解析用）  
- `bridge_inferred_edges.tsv`  
- 既存の augment（bridge export、colourful 第2パス、gap export など）

recall は「巨大成分を BK する」のではなく、**選択的に足す**ことで拾う、というのが北極星です。

## 6. やってはいけないこと

| やってはいけないこと | 理由 |
|----------------------|------|
| 分割後の小成分を **直積で閉じる**（成分内の全クロスゲノムペアをオーソログにする） | link_all。ペア数が 10⁶〜になり precision が崩れる |
| `prune_weak` の quantile を上げるだけ | 一度切りでは糊が残る。上げ過ぎると本物の辺も落ちて precision 悪化 |
| 巨大成分を `max_components` で丸ごと捨てるだけで済ませる | 中の本物の 1to1 まで消える。壊すことではない |
| 列挙を速くするために、弱い辺を全部永久削除する | GraphML / augment で使う証拠まで失う |

## 7. 実装の優先順（まとめ）

実装するなら、次の順が小さいパッチから始められます。

1. **列挙成分を 1to1（または高 `mutual_ci`）backbone で切り直す**  
   - 挿入位置: `.graph2df()` の直前、または `.graph2df` 内の成分分割  
   - GraphML 用グラフと、列挙用辺集合を分ける  
2. 煙テスト（D1）で「巨大成分ジョブが終わること」を確認  
3. BUSCO / compare_tools で precision・recall・ペア数が北極星を満たすか見る  
4. 必要なら **反復 flooding**（サイズ目標付き）を足す  
5. 最後に `max_components` / スペクトル分割を例外処理として残す  

API のイメージ（案）:

```r
reorgOrthopairs(
  ...,
  # 既存
  graph_qc = "prune_weak",
  max_components = Inf,
  # 追加案（名前は実装時に確定）
  subgraph_backbone = c("1to1", "high_mutual_ci", "all"),
  backbone_min_mutual_ci = 0.5,
  flood_until_max_vertices = 200L  # NULL なら flooding しない
)
```

回帰のため、`subgraph_backbone = "all"`（いまと同じ）を残せるようにすると安全です。

## 8. たとえ話（全体の直感）

都市を道路で結んだ地図を想像してください。

- **頂点** = 建物（遺伝子）  
- **辺** = 道路（オーソログ候補）  
- **強い 1to1** = 幹線道路  
- **弱い MtoM / bridge** = 細い抜け道や仮設の橋  

colorful 列挙は、「各国（種）から代表者を最大1人ずつ選ぶツアー経路」を、地図上のつながりから全部探す作業です。

細い抜け道まで全部残した地図だと、大陸全体が1つの巨大な迷路になり、ツアーの候補探索が終わりません。  
幹線道路だけで地図を切り直すと、小さな地区に分かれ、各地区のツアーはすぐ終わります。  
細い道は消したのではなく、**後から「この地区とあの地区を、条件付きでつなぐ」作業（augment）に回す**、というのがこの文書の提案です。

## 9. 用語ミニ辞典

| 用語 | 短い説明 |
|------|----------|
| **RBH / mutual_ci** | 相互最良ヒットと、その信頼度スコア |
| **1to1 / 1toM / Mto1 / MtoM** | ペア内の対応の型。1対1か、多対多か |
| **bridge** | 直接辺が無い遠いゲノム対を、中間ゲノム経由で推論した辺 |
| **連結成分** | 辺でつながっている頂点の塊 |
| **colorful** | 種（色）ごとに頂点が高々1つ |
| **Bron–Kerbosch** | 極大クリークを列挙する古典的アルゴリズム |
| **flooding** | 弱い辺を繰り返し落として巨大成分を分割する考え方 |
| **backbone** | 列挙に使う強い辺だけの骨格 |
| **augment** | 列挙後に、欠けたペアを選択的に足す後処理 |
| **link_all** | 成分内の全クロスゲノムペアをオーソログにする（禁止寄り） |
| **RSS** | プロセスが実際に使っているメモリ量。増えない＝大きな新規確保をしていないことが多い |
| **max_components** | これより大きい成分は列挙をスキップする上限 |

## 11. 一文での結論

巨大成分を列挙前に壊すとは、**弱い辺でつながった巨大迷路ごと Bron–Kerbosch に投げないこと**であり、具体的には **列挙用の連結成分を 1to1（または高スコア）の backbone で切り直し、弱い辺は augment に残す**ことです。
